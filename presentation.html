Problem Statement

What Problem Does This Project Solve?

Overcoming computational bottlenecks in conventional music players and media storage.

PROBLEM DEFINITION // SLIDE 02
⚠️
1. Linear Traversal Latency

Naive systems store audio tracks in unindexed flat arrays. As libraries scale to 50,000+ tracks, searching by title or finding song metadata degrades to O(n) linear time, causing audio stutters and sluggish search latency.

  • High CPU utilization during continuous text query.
  • Cache-miss penalties with unmanaged memory.
O(n) → O(1) Target
🔄
2. Queue Shifts & Bloat

Standard queue implementations on plain arrays require expensive O(n) element shifts every time a song finishes playing, or result in wasted buffer space when head pointers simply increment without wrapping.

  • Frequent reallocations & fragmented heap.
  • Unbounded play history memory footprints.
Circular Buffer Required
📊
3. Dynamic Top Charts Overhead

Calculating live "Top 10 Most Played" or "Highest Rated" songs traditionally forces an expensive full-table sort costing O(n log n) on every single playback event, starving playback threads of precious clock cycles.

  • Heavy re-sort latency on frequent updates.
  • Lack of priority queue semantics.
O(log n) Heap Solution
Target: Zero-allocation playback loop, sub-millisecond retrieval, constant memory bounds

Music Library: Doubly Linked List (DLL)

Bi-directional sequential traversal and dynamic memory management for the track catalog.

DATA STRUCTURE 1 // SLIDE 05
Why Doubly Linked List?

Music players require seamless Next Song and Previous Song operations. A Doubly Linked List provides pointers in both directions (prev and next), eliminating the need to search backward.

  • O(1) Insertion: Constant-time appending to tail as new songs are imported.
  • O(1) Local Deletion: Removing a track from a known pointer requires updating two adjacent pointers.
  • Bidirectional Display: Supports forward traversal and reverse traversal (lib_display_reverse).
Append: O(1) | Bidirectional Step: O(1)
Memory Representation

[NULL] ← [Song 1: Blinding Lights] ↔ [Song 2: Starboy] ↔ [Song 3: After Hours] → [NULL]

// library.h & library.c — Core DLL Implementation
typedef struct LibNode { Song song; struct LibNode *prev; struct LibNode *next; } LibNode; typedef struct Library { LibNode *head; LibNode *tail; int size; int next_id; } Library; int lib_add_song(Library *lib, const char *title, ...) { LibNode *node = (LibNode*)malloc(sizeof(LibNode)); node->song = song_create(lib->next_id++, title, ...); node->next = NULL; node->prev = lib->tail; if (!lib->head) { lib->head = node; } else { lib->tail->next = node; } lib->tail = node; lib->size++; return node->song.id; }

Play Queue (Circular Queue) & History (Stack)

FIFO scheduling for upcoming songs and LIFO tracking for playback history & back navigation.

DATA STRUCTURES 2 & 3 // SLIDE 06
🔄
Circular Queue (FIFO) — Up Next

Constant time O(1) buffer without element shifting

// queue.c — Modular arithmetic wrap-around int queue_enqueue(Queue *q, Song song) { if (q->count == QUEUE_MAX_SIZE) return -1; q->data[q->rear] = song; // Wrap index seamlessly using modulo q->rear = (q->rear + 1) % QUEUE_MAX_SIZE; q->count++; return 0; }
  • Zero Wasted Space: Rear pointer wraps back to index 0.
  • O(1) Enqueue & Dequeue: Next track plays instantly.
  • Fixed size guarantees bounded memory on embedded chips.
🥞
History Stack (LIFO) — Rewind

Instantaneous "Previous Song" tracking & undo

// stack.c — Push on play, Pop to rewind int stack_push(Stack *s, Song song) { if (s->top >= STACK_MAX_SIZE - 1) return -1; s->data[++(s->top)] = song; return 0; } int stack_pop(Stack *s, Song *out) { if (s->top < 0) return -1; *out = s->data[(s->top)--]; return 0; }
  • Natural Audio Reversal: Most recently played song sits on top.
  • O(1) Push / Pop / Peek: Zero overhead during track transitions.
Circular Queue: Modulo Wrap Stack: Array-backed LIFO Both O(1) Time

Dual Indexing: BST & Hash Table

O(log n) lexicographical search coupled with O(1) average constant-time ID retrieval.

DATA STRUCTURES 4 & 5 // SLIDE 07
1. Binary Search Tree (BST)

Enables O(log n) search by song title and ordered alphabetical display using in-order traversal:

BSTNode *bst_search(BST *tree, const char *title) { BSTNode *curr = tree->root; while (curr) { int cmp = strcasecmp(title, curr->song.title); if (cmp == 0) return curr; curr = (cmp < 0) ? curr->left : curr->right; } return NULL; }
  • In-Order Traversal (L-Root-R): Generates sorted catalog in O(n) without running extra sort routines.
2. Hash Table with Chaining

Maps internal numeric song IDs to song memory with O(1) average lookup using separate chaining:

// Modular hash using prime table size (101) int index = song.id % HASH_TABLE_SIZE; Song *hash_lookup(HashTable *ht, int id) { int idx = id % HASH_TABLE_SIZE; HashNode *node = ht->buckets[idx]; while (node) { if (node->song.id == id) return &node->song; node = node->next; } return NULL; }
  • Collision Handling: Singly linked list chains on each bucket.
  • Zero Delay: UI click on song ID resolves song details in 0.001ms.
Search: BST O(log n) ID Lookup: Hash Table O(1) Table Size: 101 Prime Buckets

Top Charts & Ranking: Max-Heap

Complete binary tree maintaining real-time trending charts by play count or user rating.

DATA STRUCTURE 6 // SLIDE 08
Why Max-Heap Beats Full Sorting

In a commercial streaming app, users constantly want to know: "What is the #1 trending song?" or "Show me the Top 5 tracks."

Running a full sort takes O(n log n) every time play count increments. A Max-Heap:

  • Peeks Top Song: Exactly O(1) time at data[0].
  • Heapify / Insert: Logarithmic O(log n) via bubble-up/down.
  • Build Heap: Can convert an entire library array to a heap in O(n) linear time.
  • Dual Mode: Configurable for HEAP_BY_PLAYS or HEAP_BY_RATING.
Root Element = Highest Metric at O(1)
// heap.c — Sift Down operation for Max-Heap extraction
static void heapify_down(Heap *h, int i) { int largest = i; int left = 2 * i + 1; int right = 2 * i + 2; if (left < h->size && heap_compare(h, left, largest) > 0) largest = left; if (right < h->size && heap_compare(h, right, largest) > 0) largest = right; if (largest != i) { Song tmp = h->data[i]; h->data[i] = h->data[largest]; h->data[largest] = tmp; heapify_down(h, largest); } }
Component: heap.c Array-based Complete Binary Tree Top-K Extraction: O(k log n)

Sorting Engine: Merge Sort & Quick Sort

Multi-attribute sorting (Title, Artist, Plays, Duration, Rating) + Binary Search on sorted data.

ALGORITHMS // SLIDE 09
Merge Sort (Stable)

Divide-and-conquer algorithm with guaranteed O(n log n) worst-case complexity.

  • Stability Preserved: If two songs have identical ratings, their original relative order is preserved.
  • Ideal for UI column sorting where secondary sort order matters.
Worst-Case: O(n log n)
Quick Sort (In-Place)

Partitioning algorithm with O(n log n) average case and minimal memory overhead.

  • Zero Extra RAM: Sorts songs directly within memory buffers.
  • Uses median/pivot strategy for fast reordering of catalog arrays.
Auxiliary Space: O(1)
Binary Search

Once tracks are sorted by title, search operations execute in O(log n) time:

  • Halves search space on every comparison step.
  • Finds any track in a 100,000-song catalog in at most 17 comparisons (vs 100,000 in linear search).
Lookups: ≤ 17 steps for 100k
Sort Keys: Title, Artist, Play Count, User Rating, Track Duration

Relational Modeling: playlist.c

Playlist Architecture: Linked List of Lists

Hierarchical data model decoupling song storage from playlist membership.

DATA STRUCTURE 7 // SLIDE 10
Pointer-Based Architecture (No Duplication)

Playlists do not duplicate song structs. Doing so would multiply memory usage and risk stale data when play counts update.

  • Two-Tier Hierarchy: The PlaylistManager maintains a singly linked list of Playlist nodes.
  • Referential Integrity: Each playlist contains a singly linked list of PLSongNode storing integer song_id references.
  • Dynamic Linking: When displaying a playlist, IDs are mapped back to actual songs via the DLL / Hash Table in constant time.
Zero Song Duplication Overhead

[PlaylistManager] → [Playlist: "Chill Beats"] → [Playlist: "Workout High"]

                         [SongID: 1] → [SongID: 4] → [SongID: 7] → NULL

Conclusion & Evolution

Key Achievements & Future Engineering Roadmap

Synthesis of accomplishments and future extensions for high-scale distributed audio.

SUMMARY // SLIDE 13
What Was Achieved
  • Complete End-to-End System: Engineered 8 interconnected classic data structures in ANSI C with zero high-level framework crutches.
  • Dual-Tier Architecture: Unified a high-speed compiled C core with a modern browser frontend over embedded sockets.
  • Mathematical Optimization: Reduced key query operations from O(n) to O(1) and O(log n).
  • Memory Safety: Strict pointer validations, destructor functions (lib_destroy, bst_destroy, hash_destroy) preventing memory leaks.
Future Expansion Roadmap
  • AVL / Red-Black Balancing: Self-balancing tree rotations to prevent BST degradation on sorted inputs.
  • Persistent Disk Serialization: B-Tree or SQLite storage engine for persistence across system restarts.
  • Trie Data Structure: Autocomplete prefix search (e.g. typing "Th" instantly highlights "The Weeknd").
  • DSP Audio Processing: Native Fast Fourier Transform (FFT) integration for real-time waveform visualizers.
